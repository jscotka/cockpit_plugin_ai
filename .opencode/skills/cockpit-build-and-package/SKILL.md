---
name: cockpit-build-and-package
description: Follow the target project's Cockpit package, build, development-install, and distribution conventions
---

For configuration editors, bundle a checked-in validated JSON manifest as the single schema source; do not add a runtime YAML dependency or infer types/editability from installed prose. Treat generated HTML/JS/CSS/theme files as an atomic revision, rebuild all required assets, test loaded IDs/revisions and initialization elements, and document complete deployment plus cache/reload and rollback behavior. Separate stale installed-package/cache failures from source/build failures.

Inspect the target repository and installed toolchain first. `cockpit.js` provides JavaScript APIs and transport; it does not inject Cockpit or PatternFly CSS. Verify that plugin HTML explicitly ships CSS, without relying on shell/global CSS inheritance. Deliberately choose full bundled component CSS or a small scoped local CSS layer when shell imports conflict with standalone geometry; the local layer must retain focus/disabled/error states, dark semantic tokens, responsiveness, and no global selectors. Use the validated [cockpit-podman](https://github.com/cockpit-project/cockpit-podman) pattern where appropriate, but for plain HTML keep only a small esbuild/Sass build and generated CSS; do not copy Podman's React/full distribution/Makefile machinery. Compare component imports, theme setup, and asset wiring with a known working package such as Valkey or Podman, and distinguish component CSS from shell-oriented page geometry imports. Ensure matching PatternFly versions and that CSS selectors match the HTML. Sass imports may be tree-shaken when they emit no actual selectors, so inspect generated CSS. Use a starter-kit-like structure only when it matches the target. Verify the manifest, entry points, build output, development installation, and package metadata. Do not assume `dist` is committed, add dependencies without approval, or call a generic build equivalent to RPM readiness. Run only documented, scoped checks and report unavailable packaging tools separately from source or build failures. Before declaring UI complete, inspect generated page, card, button, tabs, form, and dark-theme-token selectors, verify HTML-to-bundle asset revisions, and run the target build.

For standalone plain-HTML pages, remember that Cockpit `page.scss` and PatternFly Page CSS are shell-oriented. Do not import/use the `pf-v*-c-page` Page root or page CSS unless the complete matching Page DOM, including required main/sidebar structure, is present. Otherwise isolate page-specific layout with a unique root class, plain full-width `main` and panels, and no shell containers/sidebar/grid constraints. This restriction is about Page/layout CSS, not matching PatternFly component CSS. Verify generated selectors plus rendered desktop geometry (no accidental sidebar), visible panels, dark-theme initialization, and narrow layout. Rebuild required generated CSS after Sass changes; keep local lockfile/build dependencies if the adjacent checkout is stale, and never commit `node_modules`.

References: adjacent `../examples/pinger/`; official [packages guide](https://docs.cockpit-project.org/cockpit-guide/latest/guide/packages.html) and [starter-kit](https://github.com/cockpit-project/starter-kit). The starter-kit is a starting example; the target repository's conventions take precedence.
