---
name: cockpit-plugin-workflow
description: Discover, scope, implement, and verify Cockpit plugin changes using the target repository's current conventions
---

For schema-driven editors, require a checked-in validated JSON manifest as the authoritative bundled contract for optional categories/sections, types, ranges, defaults, help/examples, and editability; use installed man pages only for non-blocking drift checks. Use meaningful section cards only when grouping adds value; otherwise render fields directly in schema order. Newly editable options need explicit validators for structured/list, URL/path/origin/header/OAuth values, true unset/removal, absent-versus-false defaults, security warnings, and duplicate/conflict preservation. Test defensive missing-node handling, Save gating until load, conflict-aware writes, and write success separately from post-save refresh/render failures. Treat HTML/JS/CSS/theme output as one revision: fail early on stale/missing assets or required DOM, and verify loaded IDs/revisions, atomic deployment, and cache/reload behavior.

Start with the target repository's AGENTS.md, package manifest, dependencies, source, tests, and packaging. Confirm that the task is a plugin change and do not assume this suite implements one. Use current official Cockpit docs and maintained source in `../` as sources of truth. Ask about critical privilege, security, destructive-action, data, or architecture unknowns before implementation; record other assumptions. For plain HTML, explicitly decide between full bundled component CSS and a small scoped local CSS layer; the latter is valid for shell geometry conflicts only if it keeps focus/disabled/error states, dark tokens, responsiveness, and no global selectors.

Sequence work as discovery → requirements and acceptance criteria → parallel UI/backend decisions where relevant → bounded implementation → gettext/docs/tests → verification. During discovery, verify that each plugin HTML explicitly loads `cockpit.js` and explicitly loads or bundles CSS; `cockpit.js` is an API/transport library and does not inject Cockpit or PatternFly CSS. Do not look for a runtime-global CSS path. For the validated [cockpit-podman](https://github.com/cockpit-project/cockpit-podman) pattern, the JS entry imports `cockpit-dark-theme` and `patternfly/patternfly-6-cockpit.scss`; SCSS imports may include `ct-card.scss`, `page.scss`, and `global-variables`, producing package-local `dist`/CSS artifacts. A plain-HTML plugin should retain only a small esbuild/Sass build and generated CSS, not Podman's React/full distribution/Makefile machinery. Check matching PatternFly versions and CSS selectors, and follow current in-tree imports and package conventions. Assign distinct file ownership to each writer. Never edit `../` unless explicitly authorized. Use the specific workflow skills for UI, backend transport, build/package, docs, localization, and integration checks.

For UI verification, inspect generated CSS for representative selectors used by the HTML (`pf-v6-c-page`, card, button, tabs, and form) and run the target build. Sass imports may be tree-shaken if they emit no selectors. Distinguish missing npm/tools from source or build failures, and add a focused generation/build regression check when the package has a build. Rebuild required generated CSS after Sass changes, retain local lockfile/build dependencies when the adjacent checkout is stale, and never commit `node_modules`. Do not guess import paths or link unavailable source files at runtime.

For standalone HTML pages, account for shell-oriented `page.scss`: use a unique root scope, simple matching DOM, full-width main/panels, no accidental shell-sidebar grid, dark-theme initialization, and visible tab panels. Keep page-level status and empty-state elements outside CSS grids unless they are intentionally grid items, so they cannot create an empty leading cell; use `align-items: start` when card content has variable height. Correct PatternFly DOM structure for pages, tabs, forms, and titles matters as much as class names; verify rendered geometry and narrow layout. When a schema policy changes, remove obsolete read-only tabs, grids, state labels, and rendering paths rather than preserving stale UI contracts. Backend INFO/metrics must tolerate Valkey/Redis version differences and empty DB sections: successful commands indicate reachability, optional fields may use unknown/zero defaults, warnings are non-fatal, and actual command errors remain failures. After a meaningful regression is resolved, delegate `cockpit-agent-maintainer` to update guidance only when evidence supports a reusable lesson.

Useful local examples and source: `../examples/pinger/`, `../pkg/networkmanager/`, `../pkg/networkmanager/plots.js`, `../pkg/systemd/timer-dialog.jsx`, `../pkg/systemd/service-tabs.tsx`, `../pkg/lib/cockpit-components-listing-panel.tsx`, `../pkg/lib/cockpit-components-plot.jsx`, `../pkg/systemd/overview-cards/usageCard.jsx`, `../pkg/users/users.js`, and `../pkg/systemd/terminal.jsx`. Inspect their current revision before relying on details.

Official starting points: [latest guide](https://docs.cockpit-project.org/cockpit-guide/latest/guide/), [packages](https://docs.cockpit-project.org/cockpit-guide/latest/guide/packages.html), [starter-kit](https://github.com/cockpit-project/starter-kit). [Creating plugins for the Cockpit user interface](https://cockpit-project.org/blog/creating-plugins-for-the-cockpit-user-interface.html) is introductory and illustrative, not normative.
