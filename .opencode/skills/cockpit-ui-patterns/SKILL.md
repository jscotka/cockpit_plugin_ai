---
name: cockpit-ui-patterns
description: Select Cockpit-native and PatternFly UI patterns with accessible interaction and complete states
---

Inspect target dependencies and maintained in-tree examples before proposing UI. Match the visual language of existing Cockpit pages, especially `/users` and `../pkg/users/`, rather than creating an approximate standalone web design. `cockpit.js` is a JavaScript API/transport library, not a CSS loader: plugin HTML must explicitly ship CSS, with no assumption of shell/global CSS inheritance. Deliberately choose full bundled Cockpit/PatternFly component CSS or a small scoped local CSS layer when shell imports conflict with standalone geometry. A local layer is valid only with focus/disabled/error states, dark semantic tokens, responsiveness, and no global selectors. Use the validated [cockpit-podman](https://github.com/cockpit-project/cockpit-podman) asset pattern as guidance, but for plain HTML recommend only a small esbuild/Sass build and generated package-local artifact, not React/full distribution/Makefile machinery. Reuse installed primitives and patterns; keep matching PatternFly class and generated-CSS versions. Compare the chosen component imports, theme setup, and asset wiring with a known working package such as Valkey or Podman, and distinguish component Sass from shell-oriented page/layout imports. Raw HTML controls and custom CSS are acceptable only when the target package lacks an equivalent and the tradeoff is documented. Cover applicable charts, forms, modal dialogs, tabs, and dependent actions with complete keyboard, focus, accessible-name, validation, loading, empty, success, error, dark-mode, narrow-width, disabled, and localization behavior. When compacting boolean fields into inline checkbox/label controls, retain the label association and helper/error `aria-describedby` links while verifying focus, disabled, dark, and narrow-layout states. Return recommendations and local references only; feature implementation belongs to the assigned builder.

Before calling a UI complete, inspect generated CSS for representative selectors used by the HTML: `pf-v6-c-page`, card, button, tabs, and form, plus the expected dark-theme tokens. Sass imports can be tree-shaken when they emit no used selectors. Verify that HTML references the current generated CSS/JS asset revisions, run the target build, and distinguish missing npm/tools from source or build failures. Recommend focused generation/asset-contract checks when the package has a build.

For standalone plain-HTML pages, validate the rendered DOM and geometry instead of importing shell layout assumptions unchanged: Cockpit `page.scss` and PatternFly Page CSS are shell-oriented. Do not use the `pf-v*-c-page` Page root or page CSS unless the complete matching Page DOM, including required main/sidebar structure, is present. Otherwise use a unique root scope, plain full-width `main` and panels, and no sidebar/grid constraints. This does not prohibit actual PatternFly component CSS when its component DOM matches. Initialize `cockpit-dark-theme`, use required wrappers for any retained PatternFly pages/tabs/forms/titles, and check desktop sidebar placement, visible panels, full-width content, and narrow layout. Treat a static selector match as insufficient evidence.

Local patterns: `../pkg/users/`, `../pkg/users/users.js`, `../pkg/networkmanager/`, `../pkg/networkmanager/plots.js`, `../pkg/systemd/timer-dialog.jsx`, `../pkg/systemd/service-tabs.tsx`, `../pkg/lib/cockpit-components-listing-panel.tsx`, `../pkg/lib/cockpit-components-plot.jsx`, `../pkg/systemd/overview-cards/usageCard.jsx`, and `../pkg/systemd/terminal.jsx`. Treat the Valkey example's raw `valkey.css` as a functional prototype, not a Cockpit visual reference.

See [reference notes](references/ui-checklist.md). Official docs: [latest guide](https://docs.cockpit-project.org/cockpit-guide/latest/guide/) and [packages](https://docs.cockpit-project.org/cockpit-guide/latest/guide/packages.html).
