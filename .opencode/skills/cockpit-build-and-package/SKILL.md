---
name: cockpit-build-and-package
description: Follow the target project's Cockpit package, build, development-install, and distribution conventions
---

Inspect the target repository and installed toolchain first. `cockpit.js` provides JavaScript APIs and transport; it does not inject Cockpit or PatternFly CSS. Verify that plugin HTML explicitly loads `cockpit.js` and explicitly loads or bundles CSS, without relying on shell/global CSS inheritance. Ensure the CSS class version matches generated CSS (for example, `pf-v6-*` classes require matching v6 selectors). Use a starter-kit-like structure only when it matches the target. Verify the package manifest and entry points, build scripts and output directory, development installation instructions, and any RPM/package metadata or generated-file rules. Do not assume `dist` is committed, add dependencies without approval, or call a generic build equivalent to RPM readiness. Follow current Cockpit in-tree imports and package build conventions, including PatternFly/Cockpit integration, page styles, card extensions, dark theme, and spacing utilities where applicable; do not guess import paths or link unavailable source files at runtime. Run only documented, scoped checks and report unavailable packaging tools separately from source or build failures. Before declaring UI complete, inspect generated CSS for representative HTML selectors (`pf-v6-c-page`, card, button, tabs, and form), run the target build, and add a focused generation/build regression check when the package has a build.

References: adjacent `../examples/pinger/`; official [packages guide](https://docs.cockpit-project.org/cockpit-guide/latest/guide/packages.html) and [starter-kit](https://github.com/cockpit-project/starter-kit). The starter-kit is a starting example; the target repository's conventions take precedence.
